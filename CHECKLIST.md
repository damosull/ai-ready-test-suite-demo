# Review checklist for an AI-written e2e test

Used to review every test in this demo, from both branches, the same way. Each item comes from
[CONVENTIONS.md](CONVENTIONS.md); the number in brackets is the convention it enforces.

- **Blocker**: the test should not merge until this is fixed. It is wrong, misleading, flaky by
  construction, or makes the suite worse.
- **Minor**: the test works but does not read like the rest of the suite. A reviewer would ask
  for it to be changed, but would not refuse the merge over it alone.

How findings are counted is in [SCORING.md](SCORING.md): each item is judged once per ticket,
across everything that ticket's change adds or edits (spec, page objects, scenarios).

## Blockers

| ID  | Check                                                                                                                                                                                                                                                                                                                                                                                             | Conventions        |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| B1  | **Would pass with the feature broken.** If the behaviour in the ticket stopped working, at least one assertion would fail. Fails if the assertions only prove the UI responded (a dialog closed, a toast appeared, a button was clicked) and not the outcome, or if they are made on values the action never changes.                                                                             | 2.4                |
| B2  | **Misses an acceptance criterion.** Every acceptance criterion in the ticket is asserted somewhere.                                                                                                                                                                                                                                                                                               | 2.4                |
| B3  | **Duplicates a helper that exists.** No second copy of something the suite already has: a locator or action already on `DraftOrderPage`, `OrderPage`, `AddressDialog`, `HomePage` or `LoginPage`; a GraphQL helper in `e2e/lib/graphql.ts`; a lookup like `findOrderId`; a scenario constant like `PRODUCTS` or `CUSTOMER`. Includes a new page-object class for a screen an existing one covers. | 3.3, 3.7, 6.4      |
| B4  | **Hard wait.** No `waitForTimeout`, `setTimeout`-based sleep, or polling loop with a fixed delay.                                                                                                                                                                                                                                                                                                 | 7.1                |
| B5  | **Leaves data behind or bypasses the reset.** Uses Playwright's own `test` instead of `e2e/fixtures/test.ts` (no reset, no actor); tags a writing test `parallel()`; writes to `e2e/.cache/`, the dumps or the stored sessions; changes seed state outside a registered scenario.                                                                                                                 | 1.2, 4.2, 4.3      |
| B6  | **Selectors ignore the suite's locator rules.** Uses CSS class selectors, XPath, `nth-child`/positional indexes as the way to find an element, or generated ids, where a `data-test-id` or role-and-name locator exists or could be used. Includes unscoped `getByTestId("submit")`-style locators that match on more than one part of the screen.                                                | 6.1, 6.2           |
| B7  | **Arranges state inside the spec.** Creates or changes the data it needs through API calls in the spec, in `beforeEach`, or through the UI, when an existing scenario provides it or a scenario should. Starting a draft with the existing `DraftOrderPage.create` flow is the suite's own pattern and is fine.                                                                                   | 3.1, 3.2, 3.3      |
| B8  | **Depends on unstable data.** Hard-codes database ids, or asserts on values `populatedb` randomises (its product names, prices, order numbers, customers) instead of the scenario's known values.                                                                                                                                                                                                 | 2.5, 3.5, 3.6      |
| B9  | **Signs in through the UI, or with the wrong actor.** Logs in via the login form outside `login.spec.ts`; uses `admin` for a story the ticket gives to a specific permission; types credentials into a spec.                                                                                                                                                                                      | 5.1, 5.2, 5.3, 5.4 |
| B10 | **Does not compile, or lives in the wrong place.** Fails `pnpm run check-types:e2e`; is written under `e2e-legacy/` or outside `e2e/tests/`.                                                                                                                                                                                                                                                      | 1.1, 8.2           |

## Minors

| ID  | Check                                                                                                                                                                                                           | Conventions   |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| M1  | **Locators defined in the spec.** Locators or multi-step UI actions written inline in the spec rather than on the page object that covers the screen (when it is not already a B3 duplicate).                   | 6.3, 6.4      |
| M2  | **Page-object style.** New page-object members are not `readonly` fields initialised from `this.page`, or the class does not use `constructor(readonly page: Page) {}`.                                         | 6.3           |
| M3  | **No Arrange / Act / Assert comments.**                                                                                                                                                                         | 2.1           |
| M4  | **Not one story with steps.** Several stages in one test without `test.step`, or one story split across tests that each repeat the set-up.                                                                      | 2.2           |
| M5  | **Title or tag.** Title does not say what behaviour is checked, or the `#e2e` tag is missing.                                                                                                                   | 1.4           |
| M6  | **No header comment** saying what the spec covers and why.                                                                                                                                                      | 1.5           |
| M7  | **Not web-first.** Reads text or state out of the page and asserts on the copy (`expect(await x.textContent())`, `isVisible()` in an `if`/`expect`) where a web-first assertion would do.                       | 2.3           |
| M8  | **Expected values typed in.** Literals instead of the scenario's exported constants (including the scenario name itself), or arithmetic without the guard the suite uses; money not compared as `toFixed(2)`.   | 2.5, 2.6, 3.1 |
| M9  | **Unneeded cleanup or uniqueness.** `afterEach`/`afterAll` deletes, "delete if exists" steps, timestamped or random names.                                                                                      | 4.1           |
| M10 | **Timeouts, retries or waits the suite does not use.** Per-test `timeout`/`retries`, explicit `{ timeout }` on actions or assertions without a stated reason, `networkidle`, `waitForLoadState` used as a wait. | 4.4, 7.2, 7.3 |
| M11 | **Imports.** Missing `.ts` extension on relative imports, or `test`/`expect` taken from `@playwright/test` _in addition to_ the fixture (types are fine).                                                       | 1.2, 1.3      |
| M12 | **Type looseness.** `any`, untyped `gql` calls, or casts where a type would do.                                                                                                                                 | 8.1           |
| M13 | **Comments that narrate.** Comments restating the next line, or generated boilerplate ("// Step 1: navigate"), instead of explaining why.                                                                       | 8.3           |
